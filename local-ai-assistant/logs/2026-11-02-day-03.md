# Day 3 — Memory Architecture & Reliability

**Project:** Buer — Local AI Assistant  
**Focus:** Persistent memory, Obsidian integration, safety and future architecture

## What I worked on

### 1. Obsidian memory vault

Established the Obsidian-based memory structure for Buer.

- Created a dedicated memory vault with separate areas for Buer's knowledge, personal reference notes, projects, daily logs and archives.
- Defined the purpose of `VAULT-INDEX.md` and `buer_config.md`.
- Established rules for memory ownership, persistence, conflicts and approval.
- Made the `Manual/` directory permanently read-only for Buer. It can read and reference these notes but must never modify them.

### 2. Memory writing and editing

Worked on the systems that allow Buer to maintain its Markdown memories.

- Added dedicated memory-writing and editing modules.
- Implemented previews and approval before persistent changes.
- Added backups and verification for approved edits.
- Restricted writing to permitted Buer-owned memory locations.
- Added protection against duplicate information and unsupported facts.

**Automated tests:** Previously reported results included 102 passing memory-writer tests and 83 passing memory-editor tests. These results still need to be checked against the latest code.

### 3. Memory retrieval and reliability

Testing exposed important problems in Buer's behaviour:

- Incorrect claims about information stored in its own memory.
- False claims of accessing Windows hardware information.
- Incorrect answers despite the correct information existing in the vault.
- Inconsistent handling of information shared between Buer's memory and the read-only Manual notes.

These issues showed that having a memory system is not enough. Buer also needs to understand where information came from and whether the available evidence actually supports its answer.

### 4. Architecture decisions

Defined the next direction for Buer's memory system.

The chosen approach is **hybrid experience memory**:

- Recent conversation history provides short-term context.
- Important experiences are extracted and retained in SQLite.
- Useful long-term knowledge is curated in the Obsidian vault.
- Important experiences are retained rather than automatically expiring after a fixed period.
- Repeated feedback can eventually become proposed behavioural improvements.

Future retrieval will combine keyword search with semantic search.

## Problems and limitations

The memory-writing and editing systems have automated tests, but the actual GUI behaviour is not yet reliable.

The biggest issue is the gap between what Buer claims to have done and what the application actually does.

Buer has no Windows hardware-detection tools, so it must never pretend to have inspected the system. It also needs better source attribution and conflict detection.

Daily logs, project memory, persistent chat history and improved retrieval are still future work.

## Next steps

1. Improve memory retrieval and preserve source attribution.
2. Introduce evidence states: Supported, Partial, Conflicting and Unknown.
3. Compare Buer's hardware memory with the read-only Manual reference when answering hardware questions.
4. Implement SQLite-based experience memory.
5. Connect recent conversation history with selective experience capture.
6. Later, introduce memory consolidation and semantic retrieval.

## Current status

Day 3 established the foundations for a more capable memory architecture, but reliability remains unfinished.

The next priority is not adding more features. It is making sure Buer can correctly retrieve, understand and use the information it already has.
